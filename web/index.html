00 — The premise

You shouldn't have to rent your own front door.

Ring and Nest work beautifully, right up until you stop paying — and then your recordings are gone. This started from one stubborn question: what would it take to own every layer instead?

01 — The perimeter

Sensors on a network of their own.

Motion and door sensors are ESP32-WROOM nodes, and they never touch your home Wi-Fi. They join a separate access point published by the console — so a compromised sensor cannot reach your laptop.

02 — The chain

Five devices, five different jobs.

A single sensor trip crosses two microcontrollers, a Raspberry Pi and your phone. Every hop is a different processor, a different network and a different failure mode. Deciding who owns what — state, credentials, the camera — was most of the actual engineering.

03 — The wire

Two chips, one wire, no library to save you.

The console's radio and its display talk over bare UART, so the protocol is ours to define: a sync word, a command byte, a length, the payload, a checksum. Framing and integrity had to be specified before a single byte moved.

04 — The eye

It knows a person from a cat.

The Pi runs MobileNet-SSD through OpenCV and only raises an alert for a person. A pet or a moving curtain produces frames but never a notification — which is exactly the failure mode that makes naive motion detection unbearable to live with.

05 — The secrets

Four secrets, four different lifetimes.

Your Wi-Fi password, the sensor network's key, a per-sensor identity and the disarm PIN are deliberately separate things. Collapsing network trust and application trust into one shared password is how these systems usually fail.

06 — The cloud, deleted

Then we removed the monthly bill.

Phase 1 leaned on a rented server and object storage. Phase 2 moved the hub into the house: the Pi owns the camera, fans one feed out to live video and recording, and pushes clips to your own Drive.

07 — What's next

One pipeline, more things plugged into it.

Every new device — window sensors, a curtain that closes when an alert fires, a local siren — is worth building only because the event pipeline underneath is already the same for all of them.

The engineering

Seven problems worth talking about

Every claim carries its real status. Nothing is called shipped unless you can run it today.

  1. 01

    Distributed multi-device architecture

    Five components with genuinely separate responsibilities across three networks: sensor nodes, a console, a Pi hub, a mobile client and storage. Boundaries are explicit — the Pi owns the camera and system state, the console owns the keypad and the PIN.

    Pi hub, mobile client and storage run today

    Console-to-hub transport still an open decision

    Partial
  2. 02

    A custom wire protocol

    SYNC · CMD · LEN · PAYLOAD · CRC — framing, a defined command set, length-prefixed payloads, integrity checks, timeouts, acknowledgements and explicit handling for corrupt frames. Specified in full before implementation, because debugging an unframed serial link is misery.

    Complete specification in the architecture document

    Firmware is receive-only so far

    Shipped
  3. 03

    On-device computer vision

    MobileNet-SSD via OpenCV's DNN module, running on the Pi against the shared camera feed. Detection is class-gated, not motion-gated: only a person raises an event, and a cooldown collapses one intruder into one alert instead of twenty.

    Two decisions made it survivable. Inference is decoupled from frame rate, so a slow model never backs up the video buffer. And it reads the network stream rather than the camera device, because exactly one process is allowed to own the hardware.

    17 unit tests, no camera required to run them

    Model weights verified by checksum, never committed

    Shipped
  4. 04

    Bounded retry and recovery

    Failures are enumerated rather than lumped into "connection failed": missing network, weak signal, serial timeout, a device rebooting mid-provision. Retries back off, then stop and report — instead of spinning forever and hiding a dead component behind a busy log.

    Shipped and unit-tested in the detector

    Firmware failure table not fully implemented

    Partial
  5. 05

    Secure device provisioning

    An unconfigured device publishes its own setup network with unique-per-unit credentials, takes Wi-Fi details over that isolated link, then generates and distributes a sensor-network key. Credentials live in memory during setup and in flash afterwards — never in the repository.

    Setup wizard, PIN and key generation run today

    Per-sensor identity not in firmware yet

    Partial
  6. 06

    Local-first edge computing

    A security system that stops working when the internet does is not a security system. One process owns the camera and fans a single feed out to live view, recording and detection at once. All three are local; the network is only needed to tell you.

    One publisher, three consumers, no contention

    Shipped
  7. 07

    Deployment and operations

    One command pushes the hub to the Pi, runs the test suite before installing, and manages three services with a boot rule that stops the setup server and the product hub ever fighting over the same port. Health and detector state are queryable over HTTP.

    Scripted deploy, service units, tests gate install

    No hosted CI pipeline yet

    Partial
The arc

Three phases, one system

The same product rebuilt twice, each time to remove a dependency we didn't want to live with.

  1. Phase 1 Shipped

    The cloud version

    Built at HackED 2025. A Raspberry Pi and a cheap camera, an ESP32 for Wi-Fi provisioning, a Node.js backend on a rented EC2 instance storing clips in S3, and an Android app in Jetpack Compose. Alerts arrived over server-sent events in under a second: a full-screen "was it you?" prompt, one tap from a 911 call.

    It worked end to end — hardware to cloud to phone. It also arrived with a monthly bill and someone else's servers holding the footage.

    • Raspberry Pi + camera
    • ESP32 provisioning
    • Node.js on EC2
    • Clips in S3
    • HLS live view
    • SSE alerts
    • Jetpack Compose
    • Guest OTP codes
    • Scheduled arming
  2. Phase 2 You are here

    Self-hosted, and it can see

    Everything Phase 1 did, with the rented infrastructure removed. The Pi is the hub: it owns the camera, publishes one feed that live video, recording and detection all share, caches clips locally and uploads to your Drive. Remote viewing goes through a private tunnel.

    And the thing Phase 1 listed as future work is now real: OpenCV object detection runs on the Pi and tells a person from a pet before deciding to wake you. The sensors grew into a proper ESP32-S3 console with a touchscreen and keypad, and the app was rebuilt in React Native.

    • ESP32-S3 console
    • Keypad PIN disarm
    • ESP32 motion sensors
    • Raspberry Pi hub
    • OpenCV person detection
    • WebRTC live view
    • Clips to your Drive
    • Private tunnel
    • React Native app
    • EC2 + S3
  3. Phase 3 Planned

    A self-hosted ecosystem

    The event pipeline is the product. Phase 3 plugs more of the house into it: window and door contacts on the same relay, a smart curtain that physically closes when an alert fires, zone arming so you can sleep with the upstairs disarmed, and a local siren so the house still responds with the internet down.

    The infrastructure work that unlocks it: closing the console-to-hub transport, over-the-air firmware updates, and letting the camera and the sensor network corroborate each other instead of alerting independently.

    • Window / door contacts
    • Smart curtain actuation
    • Zone arming
    • Local siren
    • OTA updates
    • Sensor + vision corroboration
